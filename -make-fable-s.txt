# /make-fable-skill — Generate a frontier-grade engineering skill for THIS project

You are about to create a project-specific engineering skill that makes ANY Claude model (Haiku/Sonnet/Opus) work on this repository at frontier quality. The output is a single file: `.claude/skills/<project-slug>-engineering/SKILL.md` in the current repo, which every future session will auto-discover.

The quality bar: after this skill exists, a model that has never seen this repo should — on its first task — read the right context silently, back every claim with `file:line` evidence, respect the project's invariants, change the minimum, verify what it shipped, and record what it learned.

Work through the five phases below. Do not skip Phase 1 or Phase 5.

---

## Phase 1 — Repo reconnaissance (silent, evidence-first)

Investigate before writing anything. Use targeted reads/greps, not repo-wide scans:

1. **Orientation docs:** `README*`, `CLAUDE.md`, `CONTRIBUTING*`, `docs/`, `AI/` or similar knowledge folders, ADRs/decision records. Note which exist and which are stale (spot-check 2–3 claims against code — docs that contradict code must be flagged in the skill's trust-order section).
2. **Tech stack + build:** project files (`*.csproj`, `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, Makefile, CI config). Extract the exact build/test/lint commands and what "0 errors" means here (are there pre-existing warnings to ignore? how many?).
3. **Architecture + seams:** entry points, layering, and especially the *seams* — the narrow funnels most behavior passes through (a dispatcher, a single service class, a queue, a middleware chain). Seams are where minimal changes happen; name them with file paths.
4. **Conventions:** `git log --oneline -30` for commit-message style; read 2–3 recent diffs for code style, error-handling and logging patterns, config-read patterns. Note mandatory wrappers (e.g., "use LogHelper not raw log4net", "use the shared HTTP client").
5. **Danger zones:** production-critical paths, known-issues docs, TODO/HACK clusters, anything guarded by feature flags or kill-switches, external processes/binaries the repo ships.
6. **Decision history:** rejected designs, superseded architectures, "we tried X and it failed" records. These MUST go into the skill — re-proposing rejected designs is the #1 way models waste time.

## Phase 2 — Extract the six ingredients

From Phase 1, write down (for yourself) the project-specific content:

1. **Session-start reading list** — the 2–5 files a model must read before any task, in order.
2. **Trust order** — where truth lives when sources disagree (usually: code > logs/measurements > docs > assumptions). Name the measured-numbers sources (perf findings, benchmark files, timing logs) so models quote instead of inventing.
3. **Domain quick-map** — current architecture state in ≤10 bullet lines: what shipped recently, what the build target is, the seams, the key file map.
4. **Regression invariants** — the things that must NEVER break (user-facing flows, data contracts, protocol guarantees, "the store must always be able to print"-class rules). These are the highest-value lines in the whole skill.
5. **Hard rules** — the project's non-negotiables (forbidden APIs, required wrappers, git hygiene, things never to lower/raise/delete).
6. **Verification recipe** — exact build command + expected result, how to smoke-test artifacts (not just compile), any "do NOT do X on a dev machine" traps (live queues, prod endpoints, real printers/devices).

## Phase 3 — Interview the user (only for what code can't tell you)

Ask at most 3–5 sharp questions, only about gaps: Which flows are business-critical and must never regress? Any rejected approaches not written down anywhere? Any production incidents that shaped current design? Deployment/elevation constraints? Preferred response language/verbosity?

If the user is unavailable or says "just do it", proceed with code-derived facts and mark the invariants section `[Needs Confirmation]` so the next session revisits it.

## Phase 4 — Write the SKILL.md

Create `.claude/skills/<project-slug>-engineering/SKILL.md` from the template below. Rules for filling it:

- Every project-specific claim carries a `file:line` or file-path reference you actually verified in Phase 1. No placeholder left unfilled, no invented facts.
- Keep it under ~200 lines. The skill teaches *method*; it points to docs for *content* — do not duplicate architecture docs into the skill.
- The frontmatter `description` must be pushy: models under-trigger skills, so say "ALWAYS use this skill for ANY task touching this repository… even a one-line question."
- Keep the universal sections (operating loop, evidence discipline, red-team, minimal change, verify, anti-patterns) intact — they are the method. Adapt only the examples and the project sections.
